# FMoT Rail Project Tracker

Project tracker for Nigeria's Federal Ministry of Transportation to track railway construction projects. Built by Schull Technologies.

Read `docs/screen-map.md` before any design or UI work and `docs/process-model.md` before any data-model, workflow or permissions work.

## Design work in Penpot

- Penpot 2.18, self-hosted at http://localhost:9001, reached through the `penpot` MCP server. The browser tab with the file must stay open with the MCP toggle on.
- Team "Schulltech Team", project "FMoT Rail Project Tracker".
- File "Wireframes" is the low-fidelity spec; read a wireframe board before building its hi-fi version, and never change it from the hi-fi work.
- File "FMoT Rail Tracker: Design System" is the shared library: pages 00 Cover, 01 Tokens, 02 Foundations, 03 Icons, 04 Atoms, 05 Molecules, 06 Organisms, 07 Templates, 99 Scratch. Leftovers go to 99 Scratch; nothing is deleted.
- File "FMoT Rail Tracker: UI" holds the hi-fi screens and consumes the library. Its pages and board names mirror Wireframes (screens/<id>, 1440x1024 web, 390x844 phone, 100 px gutters). Never mix library work and screen work in one file.
- The MCP plugin works only in the file it is open in; it cannot create files, switch files or publish a library. Those steps are done by hand in the Penpot dashboard.
- Pages are numbered so they sort: `01 Web Map home`, `02 Web Project view`, `03 Web Create project`, `04 Web Tasks`, `05 Setup`, `06 Mobile`.
- One board per screen, named `screens/<id>` using the ids in the screen map (`screens/w3-map-home`, `screens/m2-home`). Desktop boards are 1440x1024, phone boards 390x844, with 100 px gutters between boards.
- Layers are named `section/element`, lowercase, no spaces around the slash.
- Wireframes are low fidelity: greys, one dark accent for primary buttons, native Penpot text layers. The first two boards (`w3-map-home`, `w5-project-view`) carry raw-SVG text that will be replaced later; leave them.
- Never delete shapes, boards or pages. Read a board back after building it and fix overlaps.

## Design system rules

- Tokens are dot paths, lowercase, kebab-case words, in five sets: `core` (what it is: `color.navy.900`, `spacing.16`), `semantic` (what it is for: `color.text.secondary`, `color.status.stalled.line`, `type.body`), `component` (where it is used: `button.primary.bg`, `map.corridor.width`), and two override sets, `semantic-large-text` (font-size.* +25 percent) and `semantic-high-contrast` (darker text, borders and lines). The full catalogue is in `tools/penpot-ds-tokens.json`.
- Themes, group Mode: Light (default: core, semantic, component), Large text (adds semantic-large-text), High contrast (adds semantic-high-contrast).
- Token changes go to both files. Penpot does not share tokens through a connected library, so the Design System file and the UI file each hold their own copy of the catalogue. Change a token in the Design System file first, make the same change in the UI file, then update `tools/penpot-ds-tokens.json`. On 29 October 2026 both files held the same 265 tokens with the same values and themes.
- Themes are file-wide, and layout only reflows on the page that is open. After switching theme, open each page in turn; after a check, switch back to Light the same way. A spacing or size set by hand on a token-bound property is reset by any theme switch, so bind a token instead.
- Screens and components use semantic or component tokens only, never core tokens, and never a raw value on a shape. Library colours (`core/<family>/<step>`, `semantic/<group>/<name>`) and typographies (`type/<name>`, `type/phone/<name>`) are generated from the tokens and store their source token; regenerate them with `D.genColors()` and `D.genTypos()`.
- Status families are fixed: operational (green; also commissioned), under-construction (orange), planned (grey; identified, funded, contracted), stalled (red), draft (dashed grey). Each has `.line` for map and legend, `.fg` and `.bg` for chips. The gate strip uses the same families: passed green, current orange outline, blocked red, not started grey outline.
- Navy is the primary action colour. Nigeria green only appears in the header stripe and crest area, never on a button or as a status. The crest is a 40x40 placeholder slot; the coat of arms is not drawn.
- Type: Outfit (since 29 October 2026; it replaced Inter), fallback Source Sans Pro. Every typography token points at `font.family.ui`, so a font change is that one token in both files plus `D.genTypos()` or `setFont` on the library typographies in the Design System file.
- Accessibility: body 16 px web and 18 px phone, nothing below 13 px, body line height 1.5, 4.5:1 for text and 3:1 for UI parts in every theme, 48 px touch targets on phone, one primary action per screen, shadows no deeper than 2 px.
- Components are named `atoms/<name>`, `molecules/<name>`, `organisms/<name>`, `templates/<name>` and `icon/<name>`, all lowercase, with states and sizes as Penpot variants.

## Known limitations

- Variant switching on nested instances does not work through the plugin API (`switchVariant` fails on nested and older instances), so a few nested states (toggle positions, the draft header chip) are visual overrides, not true variants. Swap them by hand in Penpot if the variant matters.
- Some what-is-this tile kinds use generic Lucide icons as stand-ins (Equipment is a wrench; others reuse existing icons). Replace them when proper icons exist.
- Penpot themes are file-wide: Light, Large text and High contrast cannot sit side by side in one view, so the Large text proof boards only show Large text while that theme is active. Layout only reflows on the page that is open, so after a theme switch, open every page in turn.
- Penpot only re-measures text that is in the viewport. After a font, theme or text change, zoom to fit the page (or zoom into the shape) before reading sizes, exporting or running QA; boards elsewhere keep stale sizes until then.
- Instances whose text was overridden keep their own geometry, so a layout fix in a library component does not reach them through a library update. Re-apply the fix to the instances (`uiLargeTextFixes` in `tools/penpot-helpers.js`) or rebuild them from fresh instances.
- The plugin API cannot remove a token from a shape. `molecules/table-row` body rows still carry the `table.row-height` token on height although they now hug their content; a theme switch leaves them on auto, but unbind it by hand if it ever forces 48 px back.

The page 07 code (layout, wiring table, QA and the Large text fixes) is `installUI3` in `tools/penpot-helpers.js`.

## Database schema

Drizzle schema in `apps/api/src/database/schema/`, one file per area, all exported from `index.ts`. Every table has a uuid `id` (`gen_random_uuid()`), `created_at` and `updated_at`; columns are camelCase in TypeScript and snake_case in Postgres (`casing: 'snake_case'` in both the app and drizzle-kit).

- Enums only for lists the code branches on: statuses, kinds, decisions, organisation types, roles, funding routes. Lists the administrator edits on S5 are reference tables (`code`, `label`, `sort_order`, `active`) referenced by uuid foreign key: disciplines, asset_types, incident_types, return_reasons. Retire a value by setting `active = false`, never by deleting it.
- Every unique constraint and index is named explicitly in snake_case: `<table>_<columns>_key` for unique, `<table>_<columns>_idx` for b-tree, `<table>_<column>_gist` for spatial.

| Area (file) | Tables |

| Identity (`identity.ts`) | organisations, roles (the 18 built-in roles), users, invites, devices, otp_codes, refresh_tokens, used_tokens |

- Money is integer kobo in `bigint` columns named `*_kobo` (N1 = 100 kobo), read as JavaScript `bigint`; never float or numeric. Payment certificates enforce net = gross − retention − advance recovery in a check constraint.
- Distances and chainages are whole metres in `integer` columns named `*_m` (`length_m`, `chainage_from_m`, `accuracy_m`); never kilometres or decimals in the database. Format as km+m (`142+300`) only in the UI.
- Geometry is PostGIS in SRID 4326 (`geometry.ts`): `lineString()` (projects.alignment), `point()` (assets, submissions, incidents), `polygon()` (parcels.area) and `multiPolygon()` (admin_boundaries), GeoJSON in TypeScript and hex EWKB on the wire, each with a GiST index. Measure lengths as `ST_Length(alignment::geography)` (metres on the spheroid).
- Rows read back as "the latest" take their time from `clock_timestamp()` (`createdAtClock()`): otp_codes.created_at, submissions.received_at, approvals.created_at, audit_log.created_at, tasks.created_at, measurements.recorded_at, incident_actions.created_at, design_package_reviews.created_at. `now()` is fixed for a whole transaction, so it cannot order rows written in one.
- `approvals` and `audit_log` are append-only: triggers in migration 0002 reject UPDATE, DELETE and TRUNCATE. They have `created_at` only. Corrections are new rows.
- Migrations: `pnpm db:generate` (add `--custom --name=<name>` for hand-written SQL), review the SQL in `apps/api/drizzle/`, then `pnpm db:migrate`. It runs against the checked-out Neon branch and refuses `main` unless `ALLOW_MAIN_MIGRATIONS=1`. `0000_enable_postgis` must stay first. When a change removes a column and adds another in the same table, `drizzle-kit generate` asks whether it is a rename and needs a terminal; answer deliberately (create or rename) and check the SQL. Applied so far: 0000_enable_postgis, 0001_schema, 0002_append_only_triggers, 0003_evidence_gates_reference_tables, 0004_auth_token_version_family, 0005_projects_gates_lenders_boundaries, 0006_field_checks_media_clock, 0007_workflow_engine_payments_settings, 0008_progress_land_documents_security, 0009_design_review_clock, 0010_notify_reports_gate_rules (with a hand-written line marking existing tasks as already notified), 0011_generated_documents, 0012_holidays_origin_detail (holidays, projects.origin_detail), 0013_invite_short_codes (invites.short_code_digest, and the invite text with `{code}` where its wording was the original).
- `pnpm db:seed` loads reference data only from `src/database/seed-data.ts`: the four reference lists (with how each discipline is measured, linear, point or none, and the discipline each asset type counts towards), the two project-health thresholds and one due time per workflow step (`due.<workflow>.<step>`, reminder_rules), the variation limits (settings), the reminder rules (`reminder.*`) and the SMS templates (bodies inserted once, then the administrator's), all inserted once and never overwritten, the service provider Schull Technologies, 18 roles, 31 document types, 4 gate templates with 15 steps each and their prerequisites.

## Authentication and access

Phone number, SMS code and a 4-digit PIN; no passwords and no email. Code in `apps/api/src/auth`, `admin`, `scope`, `sms`, `audit`; roles and permissions in `packages/shared`.

- Phones are stored and compared in E.164 (`normalisePhone`, default region NG: 0803... becomes +234803...); invalid numbers are rejected with 400.
- Short invite codes (ABCD-2345: 8 characters without 0, O, 1 or I) go in the same text message as the link, for typing in the field app; every invite route takes either the code or the link's token, with the same expiry and single use, under the sign-in routes' throttle. Stored only as `invites.short_code_digest`, an HMAC under `JWT_REFRESH_SECRET`. An invite text the administrator edited without `{code}` gets "Code: …" added. The `admin:create` bootstrap invite has a link only.
- Secrets at rest: SMS codes, PINs, invite tokens and refresh tokens are argon2id hashes only. Invite and refresh tokens are opaque `<row id>.<secret>`; the id finds the row, the secret is checked against its hash. Audit rows and logs never hold codes, PINs, tokens or hashes; request logs redact the Authorization, Cookie and X-Pin-Confirmation headers.
- SMS goes through the `SMS_SENDER` provider, chosen by `SMS_PROVIDER`: `console` (`DevConsoleSmsSender`, the server log, refused in production) or `termii` (see Notifications below). Sign-in codes and invite links are sent from memory just after the request (`NotifyService.sendSecret`, retried, recorded without their text); they never reach the database.
- Invites: the IT administrator creates the user (`POST /api/admin/users`) as invited with an invite valid 72 hours. Contractor, consultant and lender people need the Director's confirmation first: the invite waits, the Director gets a Confirm new account task, and the SMS goes out only once the Director confirms, from that task or `POST /api/admin/invites/:id/confirm` (Director only, PIN step-up, never by the person who created the invite). The confirm_account handler makes the token inside the decision (only its hash is stored) and sends the SMS from `afterCommit`, so both paths behave the same. The invitee opens the link (`GET /api/invites/:token`), asks for a code (`POST /api/invites/code`), and accepts with code, PIN and device (`POST /api/invites/accept`), which activates the account and binds the device. Resend revokes the old invite; reset PIN clears the PIN and unlocks; deactivate revokes sessions, devices and open invites, records the replacement and moves their open tasks to the replacement.
- Sign-in: `POST /api/auth/otp/request` (same 202 whether or not the phone has an account; at most 3 per phone per 15 minutes, then 429 for everyone) and `POST /api/auth/otp/verify` (6 digits, valid 10 minutes, 5 tries) give a 10-minute ticket tied to the device. `POST /api/auth/pin/login`: a bound device needs only the PIN; a new device needs the ticket. `POST /api/auth/pin/set` sets the PIN after a reset. Five wrong PINs (sign-in or step-up) lock the account, sign it out everywhere and give the IT administrator an Unlock account task. PINs that repeat or run in sequence (1111, 1234, 4321) are refused.
- Tokens: access JWT 15 minutes (HS256, `JWT_ACCESS_SECRET`; claims sub, role, org, token version). The guard reads the user on every request, so raising `users.token_version` (lock, PIN reset, deactivate) ends every session at once. Refresh token 30 days, rotated on every use; presenting a rotated-out token revokes its whole family. Web gets it in the `fmot_refresh` cookie (httpOnly, Secure, SameSite=Strict, path /api/auth); mobile sends `X-Client: mobile` and gets it in the body. Step tokens (OTP ticket 10 minutes, PIN confirmation 2 minutes) are signed with `JWT_REFRESH_SECRET`. Both secrets are 64 random bytes in `apps/api/.env`, at least 64 characters and different from each other.
- PIN step-up: `POST /api/auth/pin/confirm` takes the PIN, the action (`STEP_UP_ACTIONS` in `@fmot/shared`: invite.confirm, membership.confirm, project.publish, gate.confirm, gate.approve, lot.confirm, section.sign_off, certificate.certify, certificate.approve, certificate.final_approve, certificate.mark_paid, baseline.approve, completion.record, completion.confirm, takeover.confirm, design.approve, design.countersign, variation.approve, variation.confirm) and the subject id, and returns a token valid 2 minutes for that user, action and subject. Every decision endpoint carries `@RequiresPinConfirmation('<action>', params => subject)` (or, on `POST /api/tasks/:id/act`, the engine asks for the step's action), reads the token from `X-Pin-Confirmation`, checks it names this action and subject, and records its jti in `used_tokens`, so a second use is refused (`pin_confirmation_used`).
- Every JWT carries `typ` and `aud` (access / fmot:api, otp_ticket / fmot:auth, pin_confirm / fmot:step-up) and each verifier accepts only its own, so no token stands in for another.
- Nightly clean-up (02:00 Lagos, `CleanupService`): OTP rows a day after they expire, used step-up tokens once expired, refresh tokens revoked more than 30 days ago.
- Guards: global throttling (120 requests a minute per IP, 10 on the sign-in routes; off in tests), a global `JwtAuthGuard` (`@Public()` opens a route), and `@RequirePermission('resource:action')` checked against `ROLE_PERMISSIONS` in `@fmot/shared`. Financial amounts (`finance:read_amounts`), security detail (`security:read_detail`) and live field positions (`field:read_live_positions`) are separate permissions. The IT administrator holds only admin and audit permissions, never a decision.
- Scope rule: every project-scoped query adds `scopeWhere(await scopes.forUser(user), { projectId, lotId })`. The Minister and Minister of State, Permanent Secretary, Director, M&E and oversight (Auditor-General included) see all projects. The security desk also sees every project, but its permissions stop at incidents, no-go segments and live field positions (no documents, gates or money). Everyone else sees the projects and lots of their confirmed, current memberships; lenders also see the projects in `project_lenders` for their organisation while the facility is in force. Contractors see only their own lots: tables without a lot column return nothing to them, except the project row itself (`projectRowOnly`). On top of scope, draft projects are visible only to their creator and the Director, rail (`ProjectAccessService`).
- Bootstrap: `pnpm admin:create --name "<name>" --phone <phone>` creates the first IT administrator in Schull Technologies and prints the invite link once; it refuses when an active IT administrator exists (add `--force`).
- Tests (`pnpm test:e2e`) run the whole app on the dev branch inside one transaction that is rolled back, with a fake SMS sender (`test/support/app.ts`); nothing is left on dev.

## Projects, map and gates

Code in `apps/api/src/projects` (wizard, gates, documents, lots and sections, map), `storage` and `workflow`.

- Storage: `StorageService` (`STORAGE` token). Development writes to `apps/api/storage/` (git-ignored); production gets an S3-compatible adapter in Step 8 (the stub throws). Uploads are multipart, streamed with busboy into storage while the sha256 and size are computed, limited to 25 MB, and typed by their first bytes and extension, never the client's Content-Type: pdf, docx, xlsx, jpg, png, kml, kmz, geojson, zip (shapefiles). A refused record removes its stored file.
- Wizard (W6, project manager): `POST /api/projects` creates a draft (optionally with a dashed placeholder line between the two towns) and makes the creator its first member; `PUT .../funding-route` creates the 15 project gates from the route's template (gate 1 in progress); `POST .../alignment` takes KML, KMZ, GeoJSON or a zipped shapefile, merges the pieces with `ST_LineMerge` into one LineString (refused if it stays in pieces or misses Nigeria), stores `length_m` from `ST_Length(geography)` and the states from `ST_Intersects` with the boundaries; `POST .../stations` places a station at its chainage with `ST_LineInterpolatePoint`; `POST .../members` adds people (external organisations wait for the Director); `POST .../documents` stores D01 and D02 on gate 1; `GET .../review` is the five-step recap with the responsibility matrix; `POST .../send-for-publishing` sets gate 1 awaiting confirmation with the minute's date, locks the draft and gives the Director a Publish project task; `POST .../publish` (Director, PIN step-up, never the creator, also a database check) passes gate 1 and makes the project identified; `POST .../return-draft` unlocks it with a return reason.
- Documents: one row per register code, gate and lot (null for project documents); uploading the same code again is a new version and needs a reason. Only the code's uploader role may upload. D21 and D31 are one document per design package or valuation, created by those endpoints, never by a loose upload. People limited to lots (contractors, and REs who are lot members only) upload to one of their lots and see only their lots' documents, nothing project-wide. Financial documents need `finance:read_amounts`, security documents `security:read_detail`. See W5.8 below.
- Gates: `GET .../gates` gives the 15 rows (kind, roles, status, dates, days waiting, evidence, uploaded by, confirmed by). Evidence gates (2 to 11): the step's uploader role attaches documents with the decision date (`POST .../gates/:no/evidence`), the approver role or a delegate confirms (`.../confirm`, PIN step-up, never the uploader) once the prerequisites have passed and the required codes are present, or returns it with a reason (`.../return`). The Director can let one person confirm one gate of one project (`POST .../gates/:no/delegate`, W5.11). Gate 1 passes only through publishing. Gates 12 to 15 are decided in the system (see Gates 12 to 15 below). Every decision writes an approvals row and an audit row. Passing a gate opens the gates whose prerequisites are now met and moves the project on: gate 1 identified, 4 funded, 8 contracted, 11 under construction, 14 commissioned, 15 operational.
- Prerequisites: each gate needs the one before it, except 9 and 10 (environment, right-of-way), which need only 4 and run beside 5 to 8; the two tracks meet at 11, which needs 8, 9 and 10.
- Lots and sections: lots are added from gate 8 on (gate 8 reached), within the line and not overlapping another open lot, and wait for the Director's Confirm. Site sections start blocked, show on the project card as blockers ("Site not available km 140+000 to km 152+000"), and become available with the Director's sign-off.
- Card for contractors: a lot-limited user gets `kind: 'lot'` with one entry per lot of theirs (chainage, progress, latest verified photo, open incidents and blocked sections), never project-wide or financial figures; everyone else gets `kind: 'project'`.
- Map: `GET /api/map/projects` is a GeoJSON FeatureCollection of the projects in scope (simplified to about 55 m), with status, current gate (the lowest gate not passed), days at gate, health, funding route, states and the contractors of the open lots the person may see (for the filter chips); `GET /api/map/layers/:name` gives the Layers panel's optional layers in the same scope: `stations` (every asset), `lots` (each open lot's stretch of the line), `no-go` (segments not lifted, `security:read_detail` only, else 403), `state-boundaries` (the 37, simplified to about 1 km, about 75 kB) and `legacy-lines` (empty until the old network is loaded); `GET /api/map/counters` counts on track, behind, stalled and drafts; `GET /api/projects` searches and filters (name or town, status, funding route, contractor, state); `GET /api/projects/:id/card` is W4 (financial percent only with `finance:read_amounts`; lot-limited contractors get 404).
- Health: stalled if the project is marked stalled or has waited 90 days at its current gate, behind after 2 x the gate's reminder days, otherwise on track; drafts have none. The two numbers are `health.behind_factor` and `health.stalled_days` in reminder_rules. They are placeholders: the ministry must confirm these thresholds before go-live.

## Field uploads

Code in `apps/api/src/field`. The phone is offline-first; the server never trusts its position or clock without the checks below.

- `POST /api/field/submissions` (multipart): a `metadata` JSON part (client_id, kind, lot_id, discipline_code, captured_at, latitude, longitude, accuracy_m, heading, device_id, mock_location, integrity_verdict, supersedes_id, weak_location, phone_chainage_m, details), `photo` (JPEG or WebP, 15 MB, two for a milestone claim) and an optional `voice` (M4A or AAC, 5 MB). `details` is validated per kind (`metadata.ts`). Idempotent on client_id: a retry gets 200 with the existing item (a racing duplicate is caught by the unique key), never a second row.
- Who submits: the site managers of the lot's contractor, and the lot's resident engineer (photos for verify on site, and incidents). The device must be bound to the user (403 `device_not_bound`).
- Automatic checks, stored in `check_results` as pass, warn or fail with a reason: `chainage` (ST_LineLocatePoint x length, offset by geography), `corridor` (within `projects.corridor_buffer_m`, default 500 m), `lot` (inside the lot's chainage range), `time` (not more than FIELD_MAX_FUTURE_MINUTES ahead, default 5; not older than FIELD_MAX_AGE_HOURS, default 72; warn after 24 h), `device` (fail on mock location; warn without an integrity verdict, which is stored as given until Play Integrity is verified), `location` (warn when the phone sent `weak_location` or the accuracy is worse than 25 m; its value keeps the accuracy and the chainage the phone showed), `duplicate` (the same sha256 anywhere in the project, or a dHash within 5 bits of the lot's last 500 photos; a retake is not compared with the item it replaces). The item goes to `pending_re`, `flagged` when any check fails. Nothing counts toward progress until verified.
- Media: the original is stored untouched (its sha256 recorded); sharp makes a 320 px thumbnail and a 1600 px web copy, turned upright and with EXIF removed. `GET /api/media/:id?size=thumb|web|original` returns a signed link (HMAC with MEDIA_SIGNING_SECRET, valid 5 minutes) after the visibility check; `GET /api/media/:id/content` serves it without an access token.
- Visibility: unverified items are seen only by their submitter, the lot's resident engineer and the project manager. Executives, the Director, dashboards, lenders and the public see verified items only (the card's latest photo, `GET /api/field/projects/:id/submissions`, media links). Exact coordinates (and the dot on the corridor) only with `field:read_live_positions`, or for the resident engineer of the item's lot (detail, review queue and timeline); everyone else gets the chainage.
- Review: `GET /api/field/review-queue` is the RE's queue (pending items in their lots, oldest first, flagged marked; superseded items drop out); a cron at 07:00 Lagos opens one Review queue task per RE whose queue is not empty, not a task per photo. `POST .../verify` and `.../send-back` (a return reason is required) by the resident engineer of that lot, who must belong to the lot's consultant organisation and never reviews their own item. A contractor organisation never verifies. Each decision is an approvals row and an audit row; a send back also notifies the submitter. A retake is a new submission with `supersedes_id`; the old one stays.
- Kinds: `photo` (one photo, a discipline); `daily_report` (workers, machines, weather, problem flag, optional photo and voice note; one current report per lot per day, a resend supersedes the previous one as a new version); `milestone_claim` (two photos; the milestone becomes claimed, verified when the RE verifies, planned again if sent back); `incident` (a photo or a voice note; an `incidents` row and notification rows for the lot's RE, the project's PM and every security desk officer, sent by SMS in Step 8). An RE's own photo referencing a milestone is the on-site verification: verified at once (approvals row), unless a check failed.
- For the phone: `GET /api/field/context?lat=&lon=` (the user's lots with the nearest chainage, disciplines, return reasons, incident types, server time, limits) and `GET /api/field/my-submissions?since=` (items changed since the last sync, with the discipline, chainage, who reviewed it and when, and the return reason when sent back; queued is the phone's own state).
- Tests use two committed fixture photos (`test/fixtures/site-*.jpg`, regenerate with `npx tsx test/fixtures/make-photos.ts`) and a seeded scene generator (`test/support/photos.ts`) so every case has its own picture.

## Approvals engine and task inbox

Code in `apps/api/src/workflow` (engine, rules, step-up), `tasks`, and the handlers next to their domain (`projects/workflows.ts`, `auth/invites.service.ts`, `contracts/contracts.module.ts`). Definitions in `packages/shared/src/workflows.ts`.

- One engine runs every chain: payment_certificate, design_package, variation, extension_of_time, publish_project, confirm_gate, confirm_account, confirm_lot, confirm_member, sign_off_section. Each step names its verb, role (or `gate_approver`, the template step's approver), relation (`consultant_of_lot`, `project_member`, `in_scope`), PIN step-up action (null for none), whether it is a decision, its task type and its due time in hours. One `workflow_instances` row per chain and subject holds the current step, status (in_progress, returned, completed, cancelled), the submitter and the people kept off it (`excluded_user_ids`).
- Rules, in `rules.ts` (pure, unit-tested) and applied in this order by `WorkflowEngine.refusal`: the IT administrator never acts; nobody acts on what they created or submitted, or on what names them; role (or a live delegation for that project and gate); scope (skipped for a delegate); relation; one person acts on only one decision step of a chain (the same step again after a return is fine; attach_evidence is not a decision); on a payment certificate the four approving steps (recommend, certify, approve, final approve) are four people from at least three organisations, refused as soon as three can no longer be reached. Each refusal is a 403 with a `code` (own_item, one_step_per_person, organisations, ...).
- Return always needs a return reason and goes back one step, to the person who acted on that step, as their own task; at the first step it goes to the submitter (or the handler's `returnAssignee`) as the chain's `returnTaskType`, and the instance is `returned`. Resubmitting restarts at the step that returned it.
- Every action, in one transaction: an approvals row, an audit row (`workflow.<chain>.<verb>` unless the handler keeps an older name such as gate.confirmed), the actor's task closed, the next step's task opened with `due_at` from reminder_rules (`due.<chain>.<step>`, else the definition's hours).
- Role tasks are addressed to the role and appear for everyone holding it in scope; the first to act takes it (closed for all). Deactivating a person with a replacement moves their open tasks to the replacement.
- The old endpoints (publish, gate confirm and return, lot confirm, member confirm, section sign-off, invite confirm) keep their routes, guards and PIN decorators and call `engine.act(..., { stepUpVerified: true })`.
- Inbox: `GET /api/tasks` (`?overdue=true` for past due) gives open tasks grouped by project, oldest first, with type, lot, age, due time and a one-line reason, plus `doneToday` (closed by you since Lagos midnight). It costs a fixed number of queries whatever the number of tasks: the tasks with project, lot and chain in one (delegations as a subquery), the done count, and one `reasons` call per kind of chain present (plus one each for review queue, unlock and upload tasks when present); 200 tasks of one chain cost the same as one. `GET /api/tasks/:id` is the one-screen view: title, reason, subject, documents, the chain (each step done, current or waiting, with who and when), the actions you may take, why not if none, and the PIN confirmation to ask for (`pin: { action, subjectId }`). `POST /api/tasks/:id/act` takes `action`, `returnReasonCode`, `comment`, `documentIds`, `data`, and `X-Pin-Confirmation` when the step needs it.

To add a workflow:
1. Add its key to `WORKFLOW_KEYS` and its definition to `WORKFLOWS` in `packages/shared/src/workflows.ts`; new verbs go in `ACTION_VERBS`, new PIN actions in `STEP_UP_ACTIONS`.
2. Add any new task types and approval decisions to the enums in `workflow.ts`, generate and apply a migration, and run `pnpm db:seed` for the due-time rows.
3. Register a handler in the domain module's `onModuleInit` (`engine.register({ workflows: [...], validate, onAdvance, onComplete, onReturn, afterCommit, describe, reasons, ... })`): the handler owns the subject's own status; the engine owns tasks, approvals and audit. Side effects that must not happen if the decision rolls back (an SMS) go in `afterCommit`, which runs after the transaction on every route to the decision (`/api/tasks/:id/act` or the old endpoint). `reasons` labels many items with one query (build the line with the same formatter `describe` uses), so the inbox never queries per task.
4. Start the chain where the item is submitted (`engine.start(tx, { workflow, subjectId, projectId, lotId, submittedById })`) and test it through `/api/tasks`.

## Payment certificates and variations

Code in `apps/api/src/contracts`. Amounts are kobo, sent and returned as strings of digits.

- Lot payment settings (`PUT /api/lots/:id/payment-settings`): retention in basis points (default 500, 5 percent), the advance paid and its recovery rate in basis points.
- `POST /api/lots/:id/valuations` (contractor commercial manager, multipart): period month, gross amount, quantities per discipline (JSON) and the valuation file (pdf or xlsx), stored in the register as a D31 document of the lot that the valuation points at; a corrected file after a return is a new version (`POST /api/documents/:id/versions`). It creates the certificate draft and the RE's Recommend task. Net = gross − retention − advance recovery, each rounded down; recovery is capped at the advance not yet recovered. `GET /api/lots/:id/valuations/prefill?periodMonth=` gives the screen the RE's measurement for the month.
- Chain: RE of the lot recommends, NRC project engineer certifies (PIN), Director, rail approves (PIN), Permanent Secretary (accounting officer) gives final approval (PIN), finance officer marks paid (PIN) with the payment advice D24 (a disbursement row, counterpart unless a lender is named). Statuses draft, recommended, certified, approved, final_approved, paid.
- `GET /api/lots/:id/certificates` and `GET /api/certificates/:id` show the chain (who acted, when, what remains); amounts only with `finance:read_amounts`, and the RE sees quantities without rates.
- `POST /api/projects/:id/variations` (contractor or project manager): a variation (amount) or an extension of time (days). The RE assesses, the project manager recommends, and within the limits the Director approves; above either limit the project manager attaches the BPP and FEC evidence and the Director confirms. The limits are `variation.director_limit_kobo` (N500 million) and `variation.director_limit_days` (90) in `settings`, edited by the IT administrator (`GET /api/admin/settings`, `PUT /api/admin/settings/:key`), both marked as not yet confirmed by the ministry.

## Progress, land, security, design and the project view

Code in `apps/api/src/progress` (arithmetic in `calc.ts`, unit-tested; figures in `progress.service.ts`, shared with the card and portfolio), `land`, `security`, `design`, and `projects` (documents, people, activity, portfolio).

- Progress is measured by chainage; there is no bill of quantities yet. The lot's RE submits a monthly sheet (`POST /api/lots/:id/measurements`): per line a discipline, a chainage range inside the lot (linear disciplines) or an asset (point disciplines), in progress or complete, and the verified submissions from that lot taken within 100 m of it. The state of a stretch is that of the latest line covering it (by period, then time recorded), so a later sheet paints over an earlier one.
- Percentages: linear disciplines (earthworks, drainage, track, systems) complete length over lot length; point disciplines (stations, structures) assets completed over assets of that discipline in the lot (by chainage), none meaning the discipline does not apply. Lot physical percent is the disciplines weighted by `lot_discipline_weights` (`PUT /api/lots/:id/discipline-weights`, project manager; no rows means equal weights, a discipline left out counts zero). Project physical percent is the lots weighted by contract sum (equally if a lot with progress has no sum). Financial percent is the gross of paid certificates over the open lots' contract sums.
- Rework: an in-progress line over complete work (or reopening a completed station or structure) is rework. It needs a `reason` (`rework_reason_required`), writes a `progress.rework` activity entry, and paints as `rework` on the strip map (counted as not complete; `reworkM` per discipline). Any other overlap keeps "latest wins".
- Baseline: a CSV (`discipline,month,planned_percent`, cumulative, never decreasing) from the project manager (`POST /api/lots/:id/baseline`). The first upload is revision 1 and takes effect at once. Later uploads are revisions: they need a `reason` (and may name the approved extension of time behind them, `variationId`) and wait for the Director's approval (baseline_revision chain, PIN). Only one can wait at a time (`revision_pending`). Approving one supersedes the earlier approved revision, which is kept (`GET /api/lots/:id/baseline/revisions`). Planned figures use the latest approved revision, read along straight lines between month ends; weeks behind is how long ago the plan reached today's actual percent.
- `GET /api/projects/:id/progress`: per lot and discipline actual against planned, weeks behind, monthly physical against plan and track metres laid against plan, with project figures for project-wide viewers. `GET /api/projects/:id/strip-map`: per linear discipline the merged segments along the line (across lots), per point discipline the assets, and each lot's track-laying front (furthest complete track, with its point). `GET /api/projects/:id/corridor` (`?lotId=`, `?discipline=`): GeoJSON of lots, assets, verified photo pins (exact only with `field:read_live_positions` or for the lot's RE, otherwise on the line at their chainage), open incidents for `incidents:read` (exact with live positions, description with `security:read_detail`) and no-go segments for `security:read_detail`. People limited to lots see their lots only. The card uses the same figures.
- Planning by the project manager (`progress:plan`): `POST /api/projects/:id/assets` (stations and structures on the line, lot by chainage), `POST /api/lots/:id/milestones` (with a planned date; the portfolio shows the next one).
- Land (W5.9): `POST /api/projects/:id/parcels` (linked to the site section containing it; sections created later take the parcels inside them), `POST /api/parcels/:id/status` (unpaid, disputed, queried, paid; paid needs a D17 document of the project and stays paid), grievances (`POST /api/projects/:id/grievances`, `PATCH /api/grievances/:id`, `POST /api/grievances/:id/resolve`). A section cannot be signed off while a parcel overlapping it is unpaid (`parcels_unpaid`), and the card's blocker names them: "Site not available km 100+000 to km 110+000: 2 parcels unpaid km 101+000 to km 104+800".
- Security desk: `GET /api/incidents` across every corridor in scope, `GET /api/incidents/:id`, `POST .../actions` (under review), `POST .../close`; no-go segments per project (`POST /api/projects/:id/no-go-segments`, `POST /api/no-go-segments/:id/lift` with `security:manage_no_go`; `GET` only with `security:read_detail`).
- Design (W5.7): `POST /api/lots/:id/design-packages` (the lot's contractor commercial manager; file, discipline, title) stores the drawings as a D21 of the lot and starts the chain: RE recommends, NRC engineer approves (PIN), Director, rail countersigns (PIN), ending approved for construction. Each step is also a `design_package_reviews` row. On a return to the contractor, they upload a new D21 version, then resubmit. `GET /api/lots/:id/design-packages`, `GET /api/design-packages/:id`.
- Documents (W5.8): `GET /api/projects/:id/documents` grouped by gate (code, title, version, uploader, date, lot, linked), `GET /api/documents/:id/versions`, `POST /api/documents/:id/versions` (the code's uploader role, reason required), `POST /api/documents/:id/link-gate` (the gate's uploader role links a document of another gate as evidence; submitting evidence with such a document links it too).
- People (W5.11): `GET /api/projects/:id/people`: members by organisation and role with phones, the responsibility matrix from the template (uploader, verifier, approver per gate; the verifier is the RE for gates 12 and 13), the payment, design and variation chains, and delegations.
- Activity (W5.13): `GET /api/projects/:id/activity` (filters action prefix, actor, entity, from, to; paged with `before`) for `projects:read_activity`: the approvers in the chains (Permanent Secretary, Director, project manager, NRC engineer, RE, finance officer) and the oversight viewer (auditor), on projects they see whole; a resident engineer (a lot member) sees only the entries of their lots (`audit_log.lot_id`, set by every write that concerns a lot). Kobo fields are blanked without `finance:read_amounts`.
- Portfolio (W8.2): `GET /api/portfolio` (`reports:read`; `?sort=days_at_gate|name|physical|financial&order=asc|desc`, default longest wait first): every non-draft project in scope with status, gate, days at gate, physical and financial percent (financial only with the permission), next milestone and health.

Code in `apps/api/src/projects/gates.service.ts` (`approveInSystem`, `evaluateRuleGates`, `pass`) and the chains in `projects/workflows.ts`.

## Notifications and reminders

Code in `apps/api/src/sms` (senders) and `apps/api/src/notify` (queue, dispatcher, reminders, templates, settings).

- Nothing is sent inside a request. `NotifyService.queue` inserts `notifications` rows (template, parameters, link, category). The dispatcher (every minute) claims a batch in one statement (`next_attempt_at` pushed 3 minutes ahead, `FOR UPDATE SKIP LOCKED`), so two API instances never take the same message and a dead instance's batch becomes due again; it sends them with retries (1, 5, 15, 60 minutes, then failed) and records the provider's message id. Delivery reports come from Termii's webhook (`POST /api/sms/termii/events`, `X-Termii-Signature` = HMAC-SHA512 of the raw body with `TERMII_SECRET_KEY`, hex or base64; off without the key) into `delivery_status`.
- Termii: `POST <TERMII_BASE_URL>/api/sms/send` on the `dnd` channel (the transactional route, which also reaches Do-Not-Disturb numbers), with `TERMII_API_KEY` and the approved `SMS_SENDER_ID`. Keys live in `apps/api/.env` only. Tests use a stub server (`src/sms/termii.spec.ts`), never the real API.
- Messages (`sms_templates`, edited by the IT administrator on S7; only each template's placeholders, and `{link}` / `{code}` must stay) are short plain English with a link to the exact screen under `WEB_BASE_URL` (the old name `WEB_APP_URL` is still read). No codes, amounts or other people's names, except the sign-in code itself and the invitee's own name.
- Tasks: every new task (any source) gets one message per person who must act (`tasks.notified_at` marks it done): its assignee, or the role holders who see it, minus the submitter and anyone the chain excludes. At most one task SMS per person per 15 minutes; several waiting become one "You have n new tasks" message (the others are `merged` into it).
- Preferences (`GET`/`PUT /api/me/notification-preferences`): channel (push and email come later; SMS until then), weekly digest on or off, quiet hours in Lagos time (messages wait until they end; sign-in codes do not).
- Reminders (hourly, Lagos time, `RemindersService`, rules `reminder.*` with threshold, template and active) run only on working days: Monday to Friday and not a public holiday (`HolidaysService.isWorkingDay`); one due on a weekend or holiday goes out on the next working day. The reminders: no photo or daily report from a site manager by 16:00 on an active lot; field items waiting more than 48 hours for the RE (to the project managers); chain steps past their due time (to whoever must act) and past twice it (to the Director, rail); obligations expiring within 30 and 7 days (bonds, guarantees and insurances to the project's legal officers, else the project manager; EIA conditions to the project manager); the weekly digest at 08:00 on the week's first working day, Monday unless it is a holiday (executives, the Permanent Secretary and the Director, unless turned off) with the on track, behind and stalled counters and a link to the portfolio. Each reminder has a dedupe key (per day; per ISO week for the digest; per level for expiries), so it fires once and is recorded with its rule.
- Obligations: `POST`/`GET /api/projects/:id/obligations` (`obligations:manage`: project manager and legal officer).
- Public holidays (`holidays`, S7): `GET /api/admin/holidays?year=`, `POST /api/admin/holidays` (date, name; 409 `holiday_exists`), `DELETE /api/admin/holidays/:id`, IT administrator only (`admin:reminders`), audited. The seed adds the dates known in advance for 2026 and 2027 (the fixed holidays, Good Friday and Easter Monday), one year at a time and only while that year has none, so a removed date stays removed. Eid el-Fitr, Eid el-Kabir, Id el-Maulud and weekend substitutes are added by the administrator when the Federal Government announces them.
- IT administrator: `GET`/`PUT /api/admin/reminder-rules/:code`, `GET`/`PUT /api/admin/sms-templates/:code`, `GET /api/admin/notifications` (the log with delivery status, phones masked, no text for secret messages).
- `BACKGROUND_JOBS=off` (set by the test harness) stops the dispatcher, reminders and report runner; tests run them with chosen times.

## Reports

Code in `apps/api/src/reports` (data, PDF with pdfkit and XLSX with exceljs, no browser).

- `POST /api/projects/:id/reports` (`reports:generate`; `kind` monthly or lender, `periodMonth`) answers 202 and generates in the background; the requester gets an SMS with the link when it is ready. A monthly report is the finance version (with the financial summary, stored as a financial document) when the requester has `finance:read_amounts`, otherwise the standard version. Its sections: cover, status and gate, physical against planned, the strip map (drawn), financial summary (finance version only), the month's verified photos, blockers, incidents count, land. The lender report (needs the finance permission and a facility) has the same data in a lender layout, without internal notes or anything on incidents and security.
- Monthly reports are stored as D23 and lender reports as D27 in the register, one document per project, month and version; regenerating makes a new version. `GET /api/projects/:id/reports` lists them (finance versions and lender reports only with the finance permission); `GET /api/reports/:id/file` and `GET /api/documents/:id/download` (any readable document) check access and return a signed link (`{ url, expiresAt }`, HMAC with MEDIA_SIGNING_SECRET, 5 minutes, `src/common/signed-links.ts`) to `.../content`, which needs no access token.
- Portfolio report (`POST /api/reports/portfolio`, pdf or xlsx) and Eyemark export (`POST /api/reports/eyemark`, CSV in the layout in `docs/eyemark-export.md`) belong to their requester (`GET /api/reports/portfolio`). Amounts only with the finance permission.
- Jobs are claimed with `FOR UPDATE SKIP LOCKED`; a job left `running` for 30 minutes (an instance that died) is queued again.
- On the 2nd of each month at 06:00 Lagos the previous month's monthly reports (both versions) and lender reports are queued for every project past publishing; they carry no requester (document versions uploaded by the platform have no uploader).

## Web app

Code in `apps/web`: Next.js 16 (App Router, TypeScript strict), Tailwind CSS 4, MapLibre GL 6, TanStack Query 5, Outfit from npm. `apps/web/README.md` and `HANDOVER.md` describe the screens; screen ids follow `docs/screen-map.md`.

- Run: `pnpm dev` starts the API and the web app together (`pnpm web` for the web app alone, on :3000). The browser talks only to the web app's origin: `/api/*` is forwarded to `API_ORIGIN` (default `http://localhost:4000`, `next.config.ts`), so the refresh cookie is first-party and there is no CORS. The access token lives in memory (`src/lib/api.ts`); a 401 refreshes once from the cookie and retries.
- Sample data: `NEXT_PUBLIC_API_MOCK=1 pnpm web` runs every screen on built-in data (`src/lib/mock*.ts`, written in the screen shapes): any phone, code 123456, any PIN that is not an easy one; Kaduna–Kano (`/projects/p-kk`) has every section filled.
- The contract: every API call is in `src/lib/endpoints.ts`, which maps the API's responses (`src/lib/api-shapes.ts`) onto the shapes the screens use (`src/lib/types.ts`) and the screens' requests onto the API's fields (funding route `loan` is `external_loan`, origin `presidential_directive` is `directive`, `returnReasonId` is the return reason code, gate 1's date travels with Send for publishing, kobo arrives as a string of digits, money settings are shown in naira). In sample-data mode nothing is mapped. When the API changes a response, change `api-shapes.ts` and the mapping, not the components.
- Roles, role labels, organisation rules and permissions come from `@fmot/shared` (`src/lib/roles.ts`, `src/lib/org-roles.ts`, `useCan(permission)`); errors carry a stable `code` (`apps/api/src/common/errors.ts`) with plain messages in `src/lib/messages.ts`.
- Files: documents and reports open through signed links (`GET /api/documents/:id/download`, `GET /api/reports/:id/file` return `{ url }`, valid 5 minutes, no access token needed).
- Design tokens: the `@theme` block in `src/app/globals.css` is generated from `tools/penpot-ds-tokens.json` by `pnpm tokens` (`tools/tokens-to-css.mjs`); change the tokens, not the block. Status colours only through `src/lib/status.ts` and `--color-status-*`.
- Maps: one style URL and the CC BY 4.0 boundary credit in `src/lib/map.ts` for all three maps (map home, corridor, wizard preview). `NEXT_PUBLIC_MAP_STYLE_URL` takes any MapLibre style (README: MapTiler satellite-hybrid); `public/map-style-plain.json` is the offline style the tests use.
- Security: `src/proxy.ts` sets the Content Security Policy with a nonce per request (scripts and styles only from the app with the nonce; images, connections and workers from the app and the map style's origin, plus `MAP_EXTRA_ORIGINS`; no frames or objects). The root layout reads the nonce, so every page is rendered per request. `next dev` gets `'unsafe-inline'` styles and `'unsafe-eval'`, which it needs. `next.config.ts` adds HSTS, nosniff, frame denial, referrer and permissions policies, and builds a standalone server for the Docker image. `API_ORIGIN` and `NEXT_PUBLIC_*` are fixed at build time.
- Web Step 7 forms (`src/components/forms/`): what each lot needs approved (Design, `progress:plan`), the programme and its revisions with a blank CSV template made in the page (Progress, `progress:plan`), practical completion with the PIN (Progress, `completion:record`), and bonds, guarantees, insurances and EIA conditions (Documents, `obligations:manage`; the API has no owner field, so who is reminded follows from the kind). Sample data in `src/lib/mock-forms.ts`.
- Web Step 8 actions (`src/components/forms/`): New valuation on Payments (`valuations:submit`, the lot's contractor commercial manager; it shows the RE's measurement for the month from `GET /api/lots/:id/valuations/prefill?periodMonth=` and sends it as the valuation's quantities), Add a lot on Corridor (`lots:manage`; contractors and consultants from `GET /api/organisations?type=`; the Director confirms the lot), Add a member on People (`members:manage`; people from outside the ministry wait for the Director), Send a design package on Design (`design:submit`). A draft project shows a "Not published" banner on every section and only its gates on the overview. Sample data in `src/lib/mock-step8.ts`.
- Web Step 9 brought the screens closer to the Penpot boards: map filter chips (Status, Phase, Funding, Contractor, State) with a Drafts chip, a plain legend and a Layers panel remembered on the device; task screens in two columns with "Why you" and a sentence saying what the button does (`src/lib/task-copy.ts`, keyed by the API's task types grouped by chain); the PIN as a keypad sheet (`src/components/PinPad.tsx`; four digits send it, and digits typed anywhere in the sheet count); payments as a certificate table with "Contract to date"; the overview with alerts, figures beside the gates and a small corridor map; the draft overview with "What publishing does". Deliberately not taken from the design: the notification bell (no feed in the API) and wording where the app's is plainer.
- The API client refreshes the session only on a 401 whose code is `unauthorized` (or a bare 401). Other 401s (`pin_incorrect`, `code_incorrect`) are shown as they are; retrying them after a refresh would count a wrong PIN twice towards the lock.
- Money: anything someone claims, approves or pays is shown to the kobo with `formatNairaExact` and typed amounts are turned into kobo with `nairaToKobo`, both in bigint so nothing rounds; `formatNaira` (compact) is for overviews only.
- Request bodies sent to the API are checked at compile time against its DTOs: `satisfies ApiBody<'CreateProjectDto'>` in `endpoints.ts`, with types from `@fmot/shared`.
- Tests: `pnpm --filter web test` runs the nine walkthroughs (the six in HANDOVER.md, Web Step 7's forms, Web Step 8's actions and Web Step 9's design changes) with Playwright on sample data (no API, no database, no tile server; `next dev` on :3100), and fails on any Content Security Policy violation. `pnpm --filter web test:real` runs the walkthrough against the real API (e2e-real/, see its header): invites, the wizard with a real KML, publishing with the PIN, every project section, a contractor account confirmed by the Director. It leaves its people and project on the branch it runs against.

## Field app (mobile)

Code in `apps/mobile` (README there: how to run it on a phone, the API address, what does not work in Expo Go). Expo SDK 58 (React Native 0.88, React 19.3.0), TypeScript strict, Expo Router (`src/app/`, protected routes by state: first run, signed out, locked, open), run in Expo Go on Android and iPhone; in-house only, nothing published.

- Only modules that are in Expo Go: expo-camera, expo-location, expo-sqlite (settings in its kv-store, and the outbox), expo-audio, expo-secure-store, expo-local-authentication, expo-file-system, expo-image-manipulator, expo-network, expo-localization, expo-font (Outfit from `@expo-google-fonts/outfit`), lucide-react-native with react-native-svg for the boards' icons. No custom native code. Install with `pnpm --filter mobile exec expo install <pkg>` so versions match the SDK.
- pnpm's isolated installs work with SDK 58 (Expo's monorepo guide); no `nodeLinker: hoisted`, no `.npmrc`, no Metro config. `@fmot/shared` (roles, permissions) is a workspace dependency, used built.
- Who: contractor site managers (M2 home) and consultant resident engineers (M9). Anyone else gets "This app is for site staff" and signs out.
- Sign-in (`src/lib/api.ts`): `X-Client: mobile`; the refresh token comes in the body and lives only in expo-secure-store, the access token only in memory; a device id made on first run and kept in secure storage binds the phone; number, SMS code, then PIN (entered, or set twice); invites by pasting the link or code from the invite text message (the code is too long to type; deep links come later). An ended session (401 `unauthorized`) is refreshed once, shared by waiting requests; a failed refresh forgets the session and returns to sign-in; a wrong PIN is never retried. The app opens locked on later days: the PIN through `POST /auth/pin/login`, or fingerprint or face (offered after the PIN is set, and in Settings), which renews the stored session.
- API address: `EXPO_PUBLIC_API_URL` (the origin, without `/api`), else the Mac that serves the app on port 4000 (Expo Go knows its network address). The dev API listens on every interface (`HOST`, default `::`).
- Words: `src/i18n/en.ts` holds every string; Hausa, Yorùbá and Igbo files later with the same keys (missing keys fall back to English). Large text scales every text with the tokens' Large text sizes. Text is never below 16 points, body text 18; touch targets at least 48 points, big buttons 56.
- Theme: `src/theme/tokens.ts` is generated by `pnpm tokens` (`tools/tokens-to-mobile.mjs`) from `tools/penpot-ds-tokens.json`, the same catalogue as the web; screens use `src/theme/index.ts` names, never raw values.
- Capture (M3, `src/app/capture.tsx`): the app's camera only; the shutter waits for 25 m or better, or 60 seconds with `weak_location`; the photo carries the phone's time, position, accuracy, heading, mock flag, device id, lot and `phone_chainage_m`; six what-is-this tiles (discipline codes), an optional voice note (expo-audio, 60 s), shrunk to 2048 px JPEG 0.8 with a 400 px thumbnail.
- The outbox (`src/outbox/outbox.ts`, tests against a real SQLite file through node:sqlite): one SQLite row per item keyed by the phone's client id (the API is idempotent on it), files moved into the document folder on Send, sent one at a time when the app opens, when the network returns and every 30 s while open (`OutboxProvider.tsx`; Expo Go cannot upload in the background), waiting 30 s, 2 min, 10 min, then 30 min after failures; a refusal (a 4xx other than 408 and 429) waits for Retry; full-size files deleted once accepted, the thumbnail once verified; a warning after 24 h, too old after 72 h. Items belong to the person who took them; signing out with unsent items warns and keeps them for that person only. M8 lists them with the five statuses, M7 shows what was sent back with Retake (`supersedes_id`).
- Status ladder on M2 (gap review): Queued (still on the phone, from the outbox), Sent (on the server, not yet decided), Verified, Sent back (not counting items already retaken on the server or on the phone), from `GET /field/my-submissions`; the lot and nearest chainage from `GET /field/context?lat=&lon=`; M9's count from `GET /field/review-queue`. Buttons for later steps open a "coming in the next step" screen.
- Tests: `pnpm --filter mobile test` (jest-expo: the API client's refresh, sign-out on a failed refresh, no retry of a wrong PIN, the device id across restarts; the helpers) and `pnpm --filter mobile typecheck`, both in CI. `src/lib/storage.web.ts`, `src/outbox/device.web.ts` and `metro.config.js` (wasm for expo-sqlite on the web) let the web build run in a browser only to take screenshots at phone sizes and drive the screens with a fake camera and location (`apps/mobile/docs/screens/`, with the differences from the Penpot boards); it is never given to anyone. Metro there may serve stale code after edits: restart with `--clear`.

## Code conventions

- Repository: a pnpm workspace (`apps/*`, `packages/*`), Node 26 (`.nvmrc`). `apps/api` is the backend, `packages/shared` (`@fmot/shared`: roles, permissions) holds code shared by the API, web and mobile apps; it compiles to `dist`, and the API's build, start and test scripts build it first. Root scripts: `pnpm api` (API in watch mode), `pnpm web`, `pnpm dev` (both), `pnpm db:generate`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm db:seed:demo` (demo branch only, docs/demo-data.md; it refuses main), `pnpm api:types` (OpenAPI document and shared types), `pnpm tokens` (web and mobile themes), `pnpm mobile` (the field app's dev server). The db scripts forward to the scripts of the same name in `apps/api`, which also has `db:studio`. pnpm only runs install scripts that `allowBuilds` in `pnpm-workspace.yaml` approves: esbuild is allowed, `@scarf/scarf` (install analytics) is denied. Approve new ones with `pnpm approve-builds <pkg>`.
- `packages/shared` also holds the workflow definitions (`workflows.ts`), so web and mobile can draw the chain.
- `apps/api` is an ES module package (`"type": "module"`, `nodenext`): relative imports end in `.js` (`import { DB } from '../database/database.module.js'`). Routes sit under `/api`; Swagger at `/api/docs`; `GET /api/health` checks the database and PostGIS. Config loads `apps/api/.env` (port, CORS) and the root `.env.local` (database URLs from `neon checkout`), validated by the zod schema in `src/config/env.ts`. The app uses the pooled `DATABASE_URL`; drizzle-kit uses `DATABASE_URL_UNPOOLED`. `pnpm test:e2e` runs against the checked-out Neon branch.
- API stack: Drizzle ORM with `pg` (drizzle-kit for migrations), `@nestjs/config` with zod for environment validation, class-validator and class-transformer for request DTOs, `@nestjs/swagger` for the OpenAPI document, helmet, and nestjs-pino logging (pino-pretty in development).
- Backend: NestJS 12 (TypeScript, strict), PostgreSQL with PostGIS on Neon, JWT with role-based access; scope is a row filter on every query, never trusted from the client. It replaced the earlier Java and Spring Boot plan on 2 November 2026 so the API, web and mobile apps share one language. Tests run on Vitest, linting on oxlint.
- Web: Next.js 16 with MapLibre GL (see Web app above).
- Errors: every error is `{ statusCode, code, message, details? }` from the global `ErrorFilter` (`src/common/errors.ts`). Throw Nest exceptions with `{ message, code }` for a specific code (`pin_incorrect`, `invite_expired`, `organisation_exists`); without one the code comes from the status (`not_found`, `not_allowed`, `conflict`, `too_many_requests`, ...), `validation_failed` for DTO errors, `internal_error` for anything unexpected (logged, message hidden). The web app's plain messages are keyed by these codes (`apps/web/src/lib/messages.ts`).
- The ValidationPipe (whitelist, transform) and the ErrorFilter are `APP_PIPE` and `APP_FILTER` providers in `AppModule`, so the e2e tests run them too. Every DTO property needs a class-validator decorator or the whitelist strips it.
- `HOST` (default `::`, every interface) is where the API listens, so a phone on the same network can reach the dev API; `127.0.0.1` keeps it on the machine.
- `TRUST_PROXY` (0 to 5, default 0) is the number of proxies in front of the API, used for `req.ip` (throttling, audit). Behind the web app's `/api` proxy and one load balancer it is 2.
- HTTP setup (`src/http.ts`, shared by `main.ts` and the e2e harness): body limits (JSON 256 kB, forms 64 kB; uploads have their own per-field limits in `receiveMultipart`), helmet, CORS, the `/api` prefix, trust proxy, and the OpenAPI document.
- `GET /api/ready` (readiness: 503 `not_ready` while shutting down or without the database) is separate from `GET /api/health`. On SIGTERM, `Lifecycle` (`src/common/lifecycle.ts`) marks the API not ready, stops background jobs from taking new work, gives the work in hand `SHUTDOWN_GRACE_MS` (default 20 s), and requeues what is unfinished. The pool closes last. Wrap new background jobs in `lifecycle.run()` and register their requeue with `lifecycle.onTimeout()`.
- `APP_ENV` (development, test, staging, production) says where the API runs. `NODE_ENV=production` says how. The console SMS sender is allowed with `APP_ENV=staging`, never in production. `STORAGE_DRIVER` is `local` (`STORAGE_DIR`; staging uses a persistent volume) or `s3` (still a stub). Unset, it is local in development and s3 in production.
- OpenAPI: `pnpm api:types` builds the API, writes `packages/shared/openapi.json` (Nest preview mode, no database) and generates `packages/shared/src/api-types.ts` with openapi-typescript. Commit both; CI fails if they are stale. The document describes requests exactly but no responses yet (no response DTOs), so response shapes live in `apps/web/src/lib/api-shapes.ts`.
- Deployment: `apps/api/Dockerfile` and `apps/web/Dockerfile` (multi-stage, Node 26.11.1, run as `node`, build context the repository root, `.dockerignore` keeps env files out). The image migrates with `node dist/scripts/migrate.js` (drizzle-orm's migrator, same table as drizzle-kit; it refuses `main` without `ALLOW_MAIN_MIGRATIONS=1`). Staging is Fly.io, Frankfurt (`deploy/fly/*.staging.toml`, release command for migrations). CI is `.github/workflows/ci.yml`. Deploy, roll back, restore and secret rotation are in docs/operations.md.
- Directory routes for the web screens (`src/admin/directory.ts`): `GET`/`POST /api/admin/organisations`, `GET /api/admin/users?search=`, `GET /api/admin/projects`, `GET /api/admin/audit`, `GET /api/users?role=&search=` (the wizard's and W5.11's people picker), `GET /api/organisations?type=contractor|consultant` (the add-lot drawer: active ones, id and name only, `lots:manage`), `GET /api/reference/return-reasons`. Projects: `PUT /api/projects/:id` (basics while a draft), `DELETE /api/projects/:id/stations/:stationId`.
- Drizzle pitfall: in a single-table select, `${table.column}` inside a hand-written `sql` subquery renders unqualified (`"id"`) and binds to the subquery's own table. Use a joined query, `exists()` from the query builder, or write the column qualified (`"projects"."id"`).
- Mobile: Expo (React Native) in Expo Go, offline-first, in-app camera only; see Field app (mobile) above.
- British spelling in UI text and docs.
